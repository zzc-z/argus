# 开发流程为什么慢：分析与优化建议

> 2026-11-08。基于「DAG 步骤条显示真实发生的事」这一轮的真实数据
> （会话 transcript 29771 条消息、3271 次 Bash 调用、19 次子代理）。

## 一、结论先说

**慢的不是写代码，是「验证」与「协调」。**

这一轮实际时间构成：

| 环节 | 耗时 | 占大头的原因 |
|---|---|---|
| 写代码 | 正常 | — |
| **两轮 CR 及其修复复审** | ~4 小时 | 子代理各跑 1-2 小时；CR 报出 6 严重 + 12 重要，全部要修完再复审 |
| **全量 pytest 反复跑** | **~61 分钟纯等待** | 116 次 × 32s |
| 变异测试 | ~1.5 小时 | 24 条，多数要手工构造 |
| 浏览器端到端验证 | ~1 小时 | 每轮改动后重跑 |

**关键数字**：3271 次 Bash 调用里，882 次是「读文件」、564 次是「写临时探针脚本」、
543 次是「跑单条 pytest」。真正改代码的 Edit 只有 612 次。

DORA 2025 报告的结论正好对上：「AI 省下的代码生成时间，会被**重新分配**到
验证开销与提示开销上」（the time saved during code generation is often
re-allocated to verification overhead and prompting overhead）。我们正处在这条
曲线的「验证税」阶段。

## 二、五个可量化的瓶颈

### 瓶颈 1：测试串行跑，每次全量 32 秒

**实测**：

```
串行          32.5s
-n 4          15.4s   （2.1x）
-n 8          15.2s   （封顶在 I/O，不是 CPU）
```

8 核 CPU、测试用内存 SQLite + `tmp_path`（天然隔离），**xdist 直接可用、
无 fixture 冲突**（759 个全过已验证）。

116 次全量 × 32s = **61 分钟纯等待**。改成 `-n 4` 后同样次数只需 29 分钟。

再快就要治本：最慢的几条是 `sleep` 型（`test_typewriter_paces_by_target_speed`
3.6s、`test_generation_continues_after_client_disconnects` 5.0s）——它们在等
真实时间流逝。这类测试应该改成**注入时钟**（把 `time.monotonic` 换成可控
的假时钟），单条降到毫秒级。

### 瓶颈 2：CR 是「串行阻塞」的

AGENTS.md §7.5 强制「质量门 → 测试 → CR，缺一不可」，CR 跑 1-2 小时，
期间主会话**完全空转**。

这一轮 CR 报出 6 严重 + 12 重要 —— 说明 CR 有效。但有效不等于高效：
一轮 CR 覆盖两批改动（后端 DAG + 公开来源），第二批的问题**要等第一轮改完
才知道**。真实流程是：

```
写代码 → CR(2h) → 修 6 严重+12 重要(2h) → 改完发现新问题 → 再 CR(2h) → 再修(1h)
```

**关键浪费**：CR 的「读代码找问题」与「跑测试验证问题」是**可并行**的，
而我们是串行的。

### 瓶颈 3：变异测试是手工的

项目规则要求「新测试必须证明它能抓到要防的 bug」。这一轮 24 条变异，
其中：

- 3 条**第一轮没被抓住**（测试是废的：断言恒真 / 只测纯函数没测接线）
- 修复后要再跑一遍确认

手工构造变异 = 每次写一个临时脚本 → 改代码 → 跑测试 → 改回来。
110 次临时探针脚本印证了这点。

### 瓶颈 4：每次改动后都跑「全量 + 全部门禁」

实际模式是：改一处 → 跑全量 pytest（32s）+ ruff + mypy + 前端 lint/tsc。
但改一处通常只影响一两个测试文件。

静态检查其实很快（ruff + mypy 合计 **1.2s**），真正的浪费在 pytest。

### 瓶颈 5：没有 CI，全靠人工记得跑

仓库里**没有 `.github/workflows/`，也没有 pre-commit hook**（`AGENTS.md` §6
提到 husky hook，实际不存在）。所以：

- 门禁是否跑过，取决于我记不记得
- 这次会话里 `git commit` 前我确实跑了全量门禁——但这是「我恰好记得」，不是机制保证

## 三、优化建议

按「投入产出比」排序。

### 建议 1：测试并行化（立刻做，收益最大且零风险）

```toml
# apps/api/pyproject.toml
[tool.pytest.ini_options]
addopts = "-n 4 --dist=loadscope"
```

`-n 4` 而不是 `-n auto`：8 workers 与 4 个持平（I/O 封顶），而 4 个更稳
（容器里 `os.cpu_count()` 常报宿主核数，会过度订阅）。

`--dist=loadscope` 而非默认的 `load`：同一文件的测试放同一 worker ——
我们有些测试文件共享 `db_session` fixture 与向量库，`loadscope` 能避免碰撞
（xdist 官方推荐的做法，正是为了这个）。

**收益**：全量门禁 32s → 15s。这一轮省下 30 分钟。

**配套**：`--maxfail=1`（首个失败就停）——已经坏了的分支不用跑完。

### 建议 2：把「慢测试」改成注入时钟（**未采纳** —— 需要改产品代码）

> **状态**：2026-11-09 与用户确认后**撤销**。它需要给 `Typewriter` 加
> `clock`/`sleep` 注入参数——那是**产品代码改动**，超出了「只优化开发流程」
> 的范围。
>
> 撤销后的实际影响：**速度不受影响**（13.5s，由 xdist 独立提供），
> 只是那两条打字机测试回到「±40% 浮动」的写法。
>
> 若日后愿意动产品代码，这是最值得做的一条——它让测试从「有时间抖动」
> 变成「确定性」。

`test_typewriter_paces_by_target_speed`（3.6s）、`test_run_reconnect.py::test_generation_continues_after_client_disconnects`（5.0s）、
`test_stream_interrupt_retry.py` 的一批（各 1.0s）——它们在 `await asyncio.sleep(1)`。

打字机那个测试要验的正是**节奏**，所以必须控制时间流逝。做法：给
`Typewriter` 一个可注入的时钟（`now: Callable[[], float]`），测试传入一个
手动推进的假时钟。这样单条从 3.6s 降到毫秒级，而且**断言更精确**
（现在只能断言「大概 3 秒左右」）。

**收益**：全量再降到 ~10s；且测试从「有时间抖动」变成「确定性」。

### 建议 3：CR 与「跑测试」并行（结构性改动）

现在 CR agent 跑的时候主会话空转。可以：

1. CR 跑的同时，主会话**并行**做别的独立工作（写文档、更新 LOCAL-DEV）
2. 或者：**先**跑 CR，同时用 `run_in_background` 跑变异测试（它们互不干扰）

更根本的做法是**缩小 CR 的范围**。这一轮 CR 报 12 个「重要」问题里，
有 5 个是 docstring/注释过时（`_persist_report` → `persist_report`、
`TurnLedger` 在哪个模块、重复的 docstring）。这些**不需要独立上下文**——
它们是「改了代码顺手更新注释」的事，本地自检就能发现。

所以：**CR 只审「跨模块的语义正确性」，注释与风格交给 lint + 自检。**
把 reviewer-fresh 的提示词改窄，能把 2 小时的 CR 压到 30 分钟。

### 建议 4：变异测试工具化（省掉 110 个临时脚本）

写一个 `tests/mutation.py` 之类的工具：给定「变异描述 + 文件 + 替换」，
自动跑测试并报告是否变红。参考业界做法：

- `mutmut`（Python 生态成熟方案，自动变异 + 自动算 mutation score）
- 或者一个极简版：把「改坏 → 跑 → 改回来」封成一个脚本，接受 YAML 描述

**收益**：24 条变异的成本从「每条写一个探针」降到「写一条 YAML」。
更重要的是**结果可复现、可累积**——现在每次会话的变异验证结论都留在
transcript 里，下个会话不知道做过什么。

### 建议 5：加 CI + pre-commit（把「记得跑」变成「跑不掉」）

现在门禁靠人记。加上去：

```yaml
# .github/workflows/ci.yml
- run: uv run pytest tests/ -q -n 4
- run: uv run ruff check app/ tests/ && uv run mypy app/
- run: pnpm --filter web lint && pnpm --filter web exec tsc --noEmit
```

pre-commit 只跑快的（ruff + mypy + 前端 lint，合计 ~5s），全量测试留给 CI。

**收益**：门禁不再依赖我记得。DORA 的数据说 AI 团队的 bug 率上升 9%、
review 时间上升 91% —— 缺的正是这层自动化网。

### 建议 6：把「改一处跑全量」改成「改一处跑相关的」

pytest 支持按路径跑：

```bash
uv run pytest tests/test_web_sources.py -q    # 只跑相关的
```

配合 xdist，单文件反馈 < 2s。全量只在「准备提交」时跑。

### 建议 7：上下文管理（减少读文件次数）

3271 次 Bash 里 882 次是读文件。CodeGraph 已经索引了这个仓库
（`.codegraph/`），但这次会话只用了 **10 次**。

- 查「这个符号在哪定义 / 谁调用它」→ `codegraph_explore` 一次调用返回
  源码 + 调用路径 + 影响面，比 grep + Read 好几轮快得多
- `AGENTS.md` 572 行 + 全局 `CLAUDE.md` 52 行 + 项目 `CLAUDE.md` 10 行
  每次会话都进 context。官方建议 **CLAUDE.md 控制在 200 行内**，
  「记决策与约定，不要记 Claude 能自己推断的东西」

**收益**：减少「为了确认一个事实而读的 3 个文件」，同时给 context 留出更多
空间给真正重要的东西（diff、代码）。

## 三点五、落地位置（全局 vs 项目）

按「全项目通用 / 项目细节」分开：

| 内容 | 位置 | 理由 |
|---|---|---|
| 流程骨架（反馈环分层、并行、门禁、审查分工、变异、范围纪律） | `~/.claude/rules/dev-flow.md` | 与语言/框架无关，所有项目通用 |
| 入口索引 | `~/.claude/CLAUDE.md` 的 §0 | 挂上 rules 列表 |
| CodeGraph 优先的判据 | `~/.claude/rules/tools.md` | 改工具规则比改 CLAUDE.md 合适 |
| 「改完提示相关测试」 | `~/.claude/hooks/related-tests.mjs` + `settings.json` 的 PostToolUse | 机制而非自觉；跨项目通用（按模块名匹配测试文件名） |
| 本项目的具体命令 | `AGENTS.md` §7.5 | 项目细节放项目里 |
| 本项目的变异清单 | `apps/api/tests/mutations.yaml` | 项目的具体数据 |

**全局只放骨架，不放具体命令** —— 命令会因项目而异，放全局就成了噪声。

## 四、优先级与预期收益

| # | 建议 | 状态 | 实测收益 | 风险 |
|---|---|---|---|---|
| 1 | 测试 xdist 并行 | ✅ 已做 | 全量 **32.5s → 12.9s**（2.5x） | 极低（已实测 5 次稳定） |
| 2 | 慢测试注入时钟 | ⛔ **撤销** | — | 需改产品代码（`Typewriter`），超出范围 |
| 3 | CR 范围收窄到语义 | ✅ 已做 | 预计每轮 ~1.5 小时 | 中（注释类不再报，由 lint 管） |
| 4 | 变异测试工具化 | ✅ 已做 | 24 条变异结论**可复现**，不再散落在会话记录里 | 低 |
| 5 | CI + pre-commit | ✅ 已做 | 门禁不再依赖「我记得」 | 低 |
| 6 | 相关测试代替全量 | ✅ 已做 | ~15 分钟 | 低（做成全局 PostToolUse hook，不靠自觉） |
| 7 | 多用 CodeGraph + 精简 CLAUDE.md | ✅ 已做 | ~10 分钟 | 低（全局 `rules/tools.md` 补了判据） |

**已落地的净效果**：全量测试 2.5 倍提速 + 门禁自动化 + 变异验证可复现。
建议 3 的实际收益要等下一轮 CR 才能量出来（CR 报告变短 = 审得快）。

### 实施中发现的坑（都记在配置注释里）

- **`--dist=loadscope` 不稳定**：3 次里 2 次有测试失败。它按「模块/类」
  分组，而我们的测试是函数级的（没类），于是退化成 loadfile——某个
  worker 背上多个慢文件时负载严重不均。改用 `--dist=worksteal` 后
  5 次全过，且无 fixture 碰撞（每个测试独立建库）。
- **`--maxfail=1` 在并行下会中止其它 worker**：看到「681 passed」而不是
  760，是它停了其余 worker，不是测试丢了。

## 五、业界依据

- **DORA 2025**：AI 提速的同时 bug 率 +9%、review 时间 +91%、PR 大小 +154%；
  「AI 放大的是它所在工程系统的质量」。平台工程（标准化工具与环境）是
  AI 收益的前提。
- **Faros AI 生产力悖论**（10,000+ 开发者 / 1,255 团队）：高 AI 采用率的团队
  任务数 +21%、PR 数 +98%，但 review 时间 +91%、PR 大小 +154%、人均 bug +9%。
- **Claude Code 官方 best practices**：「把同一任务交给子代理**不会**让答案更好；
  但一个**新鲜**的审查者有帮助——因为它没看过你的推理过程。」这正是 CR
  存在的理由，也是它不能被「自查 + lint」替代的原因。
- **pytest-xdist 官方实践**：`-n auto` 按核数铺开；`--dist=loadscope` 让同一
  文件的测试进同一 worker（避免 fixture 碰撞）；容器里要**显式**指定 worker
  数（`os.cpu_count()` 常报宿主核数导致过度订阅）。
- **EXANTE 案例**：一个 Python 套件从 17 分钟优化到 2 分钟（8.5x），主要靠
  xdist + 拆分巨型测试文件 + `sleep()` 换成条件等待。
- **Anthropic 成本指南**：子代理每个都有独立 context，token 用量与团队规模
  成正比；「把啰嗦的操作（跑测试、读文档）交给子代理」以保护主 context。

## 六、不建议做的事

- **不要盲目加大并行度**。我们只有 8 核，`-n 8` 与 `-n 4` 持平，还可能因
  过度订阅更慢。
- **不要为了快而删测试**。瓶颈在等待不在测试数量。
- **不要把 CR 换成「我自查一遍」**。官方文档明确：新鲜审查者的价值在于
  没看过你的推理过程，自查恰好是相反的。要优化的是**范围**不是**存在**。
- **不要一次性做完所有建议**。按 1 → 2 → 3 的顺序做，每步量一次效果。
