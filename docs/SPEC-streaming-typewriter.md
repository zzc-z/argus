# 规格：让 explore 页的正文真正打字机式地流出来

> 2026-10-30 立。修「提问后正文一下全出」——用户看到的不是流式，是「憋十几秒
> 然后整段蹦出来」。

## 背景（已实测的事实，不要重新怀疑）

**用户报的现象**：explore 页提问后，正文不是打字机效果，而是一次性全部出现。

**实测定位（2026-10-30）**：在后端直接跑 agent，把每个 `DeltaEvent` 的出栈
时刻打出来：

```
第 1 次: 60 个 delta 帧，全部在 0.0 ms 内出栈
```

60 帧在**同一瞬间**发出去 → 浏览器一个 TCP 块收齐 → React 一次渲染完。
这就是「一下全出」。

**根因在后端，不在前端。** `agent._run_turn` 原本是：

```python
async with client.messages.stream(**request) as stream:
    final = await stream.get_final_message()   # ← 攒完才返回
```

`get_final_message()` 等整条流跑完，把所有增量丢掉、拼成整段 `text`。
主循环随后调用 `_slice_for_display(result.text)` 切片——**切片切了，但所有片
在同一瞬间发出去**，切片白做了。

`TextSlicer` 的 docstring 早就写明了这件事：

> 中转站会把整个 text 块缓冲成一次 text_delta——实测 243 字符只给 1 个事件。
> 前端拿到就是「憋一下再整段蹦出来」，没有打字机效果。**这个类在后端补上
> 那一层。**

它补的是「切」，没补「什么时候送」。

## 上游到底流不流式（实测，2026-10-30，中转站 llmapi.pro）

同一个 prompt 连发 4 次，每次统计 `content_block_delta` 的到达时刻：

| 正文长度 | 帧数 | 首帧 | 末帧 | 到达跨度 |
|---|---|---|---|---|
| ~100 字 | 5 | 6.90s | 6.90s | **0.00s**（一次性到齐） |
| ~300 字 | 14 | 2.82s | 3.26s | 0.44s |
| ~1650 字 | 527 | 4.12s | 16.73s | **12.61s** |
| ~1780 字 | 105 | — | — | **10.31s** |

**规律：输出越长越流式。** 长文本上游本来就在逐字吐，我们把增量全丢了。

另一组测量（同一个「写约1000字」的 prompt 连发 4 次）：字数 1653 / 1155 /
1737 / 2164，跨度 8.7-16.5s。**上游有随机性**——这一点决定了断流重发
不能靠裁剪前缀去重（见 §3）。

断流率：长文本 10 次全部成功、0 次断流（15-30s 的流）。短文本 10 次全通。

## 改动

### 第 1 项：`_run_turn` 改成边收边发（`agent.py`）

`_run_turn` 从「返回 `TurnResult`」改成**异步生成器**，产出 `TurnChunk`：

| kind | 含义 |
|---|---|
| `"text"` | 正文增量（已过展示切片，可直接发前端） |
| `"result"` | 这一轮的收尾：usage / stop_reason / tool_calls |
| `"reset"` | 「已发出的正文作废，从头再来」 |

`_stream_turn_once` 消费上游的 `content_block_delta`，用 `Typewriter` 切片后
**立刻 yield**。`get_final_message()` 挪到流消费完之后——它只用来取 usage
和最终 content。

**只有 text 块的增量能发给用户。** tool_use 块的增量是 `input_json_delta`
（工具入参），发出去会漏出模型没打算展示的内容。

### 第 2 项：`Typewriter` —— 切片 + 控速（`stream.py`）

新增 `Typewriter`，是 `TextSlicer` 的上一层：

- `TextSlicer` 决定**在哪断**（粒度）
- `Typewriter` 决定**隔多久送**（节奏）

**为什么两件事都要做**：只切片不控速 → 上游一次性到齐时，切出来的几十片
在同一瞬间全部出栈（就是原来的 bug）；只控速不切片 → 每个 delta 帧可能只有
1 个字，DOM 里全是碎片段，Markdown 的行内格式（`**加粗**`）被切在中间。

**为什么必须是异步生成器而不是「返回列表」**：返回列表的话，等待发生在
函数**内部**——调用方一次性拿到全部片段再往下游发，等待等于白费，等完之后
所有片段仍然在同一瞬间交付出去。做成生成器，等待发生在**每次交付之前**。

**节奏是令牌桶，不是「每片固定等 N 毫秒」**。这一条是第二轮改的
（2026-10-30 用户反馈后），第一版固定间隔有两个问题：

| 问题 | 实测 |
|---|---|
| 固定间隔**太短** → 一下蹦出 | 24 字/片 + 35ms 间隔 → 800 字正文在 **0.8 秒内**全部送出。用户等了 25 秒上游，然后全文在 1 秒内涌出 |
| 固定间隔**拖慢真流式** | 720 字 + 固定 200ms 间隔 → 19.2 秒，而上游自己 5 秒就能吐完 |

令牌桶按**累计字数**算，两个问题一起解决：

- 上游缓冲（一次来 500 字）→ 累积字数远超配额 → 慢放
- 上游真流式（一个字一个字来）→ 累积字数贴着配额 → 跟随上游速度

**参数**：

| 常量 | 值 | 依据 |
|---|---|---|
| `CHUNK_SIZE` | 8 字 | 用户要「一次生成的字符一定要少」 |
| `TARGET_CHARS_PER_SECOND` | 80 字/秒 | 中文阅读 5-8 字/秒；打字机要快到能看出「在动」。800 字 → 10 秒 |
| `MIN_PIECE_INTERVAL_SECONDS` | 16ms | 只是兜底，防止「一个字一个字蹦」；主要节奏由令牌桶控制 |

`MIN_PIECE_INTERVAL_SECONDS` 定这么小，是因为它是**硬上限**——每片至少隔
这么久。定 200ms 时上限就是 40 字/秒，真流式会被拖慢 4 倍。

### 第 2.1 项：切片不能劈开词（`stream.py`）

`CHUNK_SIZE` 从 24 降到 8 之后暴露的 bug：搜索窗口缩到 12 字，逗号常落在
窗口末尾——**窗口里看不到下一个字符**，判断不了它是千分位还是真逗号，
只能放行。于是 `100,000` 被劈成 `100,` + `000`，`Blackwell` 被劈成
`Blackwel` + `l`。

两处修法：

1. `_splits_a_token` 改为看**完整缓冲区**而不是搜索窗口
2. 切点后面必须**至少还有一个字符**——否则这个标点还不能用，等下一次
   feed 补齐再判断（流式下缓冲区里是「已经收到的」文本）
3. 硬切也要避开词中间：往后找第一个非 ASCII 字母数字的位置

### 第 3 项：断流重发要发 `reset`（`agent.py` + `stream.py` + 前端）

改成真流式之后，**正文在上游还在吐的时候就已经发到前端了**。断流重发会
从头再生成一遍，而上游有随机性（字数 1653/1155/1737/2164 各不相同），
裁剪前缀去重不可靠。

所以重发前发一个 `reset` 标记，前端收到就把本轮正文清零。少了它，用户会
看到同一段正文出现两遍：前半截是断流前的，后半截是重发后的。

`DeltaEvent` 加 `reset: bool = False`。前端 `explore/page.tsx` 的 `delta`
分支先判 `reset`。

**只在确实发过东西时才发 reset**：建连就断（一个字都没发）时发它没有意义。

### 第 4 项：`_finalize` 也改成流式（`agent.py`）

强制收尾是用户能看到的最后一段正文，攒完再发就又变成「憋一下整段蹦出来」。
`_finalize` 原来返回 `(事件列表, 正文, 账本)`，现在改成异步生成器 +
一个可变容器 `_FinalizeOut`（装正文整段与新账本）。生成器只有一个 yield
通道，而这里要交回两样东西——塞进事件流当哨兵值的老做法不行（那条
「最后一项必须是账本」的不变式没有任何东西强制，漏写一个 yield 就是静默
丢 token）。

### 第 5 项：正文自动跟随底部（前端，`lib/hooks/useStickToBottom.ts`）

用户反馈：「文字出现后应该一直滚动到最底端，跟随文字走」。

**改造前**：全站**没有任何滚动跟随逻辑**——正文在增长，滚动位置不动，
用户盯着的是半截旧内容，新字在视口外看不见。

主流项目（ChatGPT / Claude / Perplexity）的标准交互是四条：

1. 内容增长时**自动滚到底**
2. 用户**手动往上滚**时**停止跟随**——不能抢用户的滚动条
3. 用户滚回底部时**恢复跟随**
4. 暂停期间给一个「回到底部」的浮标

第 2 条是关键。只做第 1 条的话，用户想回头看前面一段，正文还在增长，
页面一直把他往下拽——想看的东西被强行推走。

实现要点：

- **滚动宿主是 `.center`**（`page.module.css` 里 `overflow-y: auto`），
  不是 `window`——整页不滚，只有中间内容区滚。
- **阈值 100px**：「到底部」不能判成严格等于 0（亚像素滚动、
  `padding-bottom`、浏览器弹性滚动都会让差值停在几像素上）。
- **每次 scroll 事件都重新判断「是否在底部」**，不区分触发来源。程序
  滚动永远停在底部 → 算出来是「在底部」→ 不暂停。
  试过用「程序滚动置标志、事件里消费」的写法，标志会残留——内容增长后
  `scrollTop` 与记录值对不上，下一次**用户**滚动被误吞。
- **依赖传正文长度**（单调递增），不传对象——对象每次渲染都是新引用，
  跟随逻辑会被反复触发。
- **浮标用 `position: absolute` 相对 `.main`**（它是 `position: relative`），
  不是相对 `.center`——后者是滚动容器，absolute 相对它会跟着内容滚走。

## 不变量

- **正文一个字都不能丢**。`"".join(所有片段) == 原文`，切片与控速都只改
  节奏。
- **落盘正文与用户读到的连续文本必须一致**。`report_body` 用
  `result.text` 整段（不是展示切片）——切片边界插换行会让落盘的报告在
  每个逗号处断行（2026-10-17 CR 实测复现）。
- **任一时刻只有一个 active 节点**。节点切换必须在第一个正文片段**之前**
  发生，否则前端先收到正文、DAG 才切到 writer，顺序反了。

## 验证

### 变异测试（每个都真的被抓到）

| 变异 | 抓到它的测试 |
|---|---|
| 去掉控速（`min_interval` 恒 0） | `test_typewriter_paces_pieces` |
| `Typewriter` 改回「返回列表」 | `test_typewriter_paces_pieces` 等 4 条 |
| `_stream_turn_once` 攒完再 yield | `test_text_is_emitted_before_the_upstream_stream_ends` |
| 断流重发不发 reset | `test_retry_resets_already_sent_text` |
| 去掉「切点不能在缓冲区末尾」的守卫 | `test_numbers_are_not_split_across_pieces` |
| 硬切不避词中间 | `test_english_words_are_not_split_across_pieces` |

第三条是核心：那个测试靠「上游挂起」把「边收边发」和「攒完再发」区分开
——两种实现最终发出的正文**完全一样**，只能靠时序区分。

### 节奏验证

| 场景 | 期望 | 实测 |
|---|---|---|
| 上游缓冲（一次来 486 字） | 慢放到目标速度 | 39 字/秒（第一版参数） |
| 上游真流式（7ms/字 = 143 字/秒） | 跟随上游，不拖慢 | 720 字 / 5 秒上游 |
| 上游很慢（50ms/字 = 20 字/秒） | 跟随上游 | 不比上游自己慢 1.6 倍以上 |

### 端到端实测（真实提问，2026-10-30）

第一版（24 字/片 + 35ms 间隔）：

| 指标 | 修复前 | 第一版修复后 |
|---|---|---|
| delta 帧数 | 60 | 52 |
| 帧间隔 max | 0.0 ms | 1582 ms |
| 帧间隔 min | 0.0 ms | 33 ms |
| **< 5ms 的帧比例** | **100%** | **0%** |

但用户反馈「还是不行，一次蹦出太多字符，两次就生成完全文」——因为
800 字在 **0.8 秒内**送完（35 帧 × 24 字 × 35ms）。第二轮改成
8 字/片 + 令牌桶（80 字/秒）后：800 字要 10 秒，每 100ms 增长一段。
